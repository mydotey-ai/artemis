# ADR-021：单管理员账户接管形态（v0.4 统一认证）

版本: 1.0    更新时间: 2026-10-25

## 状态

Accepted（2026-10-25，v0.4 phase-2 设计 review 定案）

## 背景

[ADR-009](adr-009-security-by-default.md) 与架构 §5.3 记载「统一账户随 v0.4 management 接管各服务本地账户」，接管的具体形态（各服务是否委托 management 认证、SDK 数据面凭证归属）未定。v0.4 交付单管理员账户（RBAC v1.0）+ DB 持久化，需定稿对接方式，且不得破坏各服务本地单账户默认开启的既有行为与「单机 eval 零 DB」双轨约束（ADR-005）。

## 决策

接管 = **管理访问面收敛**，不引入各服务对 management 的运行时认证依赖：

- management Admin API（及 console）以单管理员 DB 账户为唯一认证源（DB 态；内存态维持配置凭证）；DB 态首启将配置凭证一次性物化（seed）进账户表，此后配置凭证在 DB 态失效。
- 各服务（registry/discovery）本地单账户保留为**服务自身凭证**：SDK 数据面（外部端口）与进程排障面（discovery `/admin/v1`、寻址端点）继续本地配置认证，零改动。
- 管理凭证与 SDK 凭证**分域**：SDK 凭证随业务方广泛分发，不与管理员凭证同源。
- 各服务管理面对 management 账户的委托机制后置 v1.0 RBAC（多用户出现真实需求时一并设计）。

## 理由

- registry 零上游依赖是架构 §2.1 既定资产；认证委托会引入 management 运行时依赖与 failover 语义（management 不可用时各服务管理面认证如何降级），代价不成比例。
- 单管理员场景下「统一」的真实消费面是 console + Admin API，均在 management 本地，无需跨服务协议。
- 凭证分域是安全语义而非妥协：SDK 凭证轮换（各服务 SCF 动态配置）与管理员改密（DB）各自独立演化。

## 否决方案

- 各服务认证委托 management（每请求/缓存验证）：破坏 registry 零依赖资产；management 故障放大为全产品管理面认证不可用。
- 账户同步下发（改密后推送各服务）：registry 无 management 通道（上游仅只读查询），需新建下发协议，单管理员场景无收益。

## 后果

- 改密运维分两处：管理面走 management 改密端点（DB 态）；各服务 SDK 凭证仍走各服务配置（动态轮换）。
- 「统一认证」的产品表述以本 ADR 语义为准（管理访问面统一），全面统一账户体系（含各服务管理面、多用户）随 v1.0 RBAC。
- 改密等账户操作的审计记录随 v0.4 phase-3 审计表落地。
