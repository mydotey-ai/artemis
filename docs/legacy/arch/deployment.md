## 1. 部署单元与打包形态

| 项 | 事实 |
|---|---|
| 部署单元 | **一个 Spring Boot 进程**，内含接入层 + 服务内核 + 管理面 + 客户端库以外的全部代码 |
| 打包形态 | fat jar（内嵌 Tomcat）**或** WAR 部署到外部 Tomcat——双入口（`artemis-package/.../App.java`，原仓库） |
| 模块是否拆部署 | **否**。Maven 模块分离（common / service / management / server / package）是构建与依赖分离，**部署仍是单体**（基线 §4 已判定「逻辑分离非部署分离」） |
| 管理面是否可独立部署 | **否**——只能运行时整体开关 `artemis.management.enabled=false` |
| 部署物 | `deployment/artemis-management.sql`（建表脚本，336 行）+ `server.xml`（外部 Tomcat 配置） |
| 容器化 / 编排 | **无 Dockerfile、无 K8s manifest、无 CI/CD、无覆盖率与静态分析**（基线 §3.7） |

> 结构性含义：管理面的代码隔离（唯一用 DB 的模块、注入点作用于数据面）**没有兑现为部署隔离**。管理面故障与数据面故障共享同一进程与同一 JVM 资源池。

## 2. 集群拓扑与成员

### 2.1 拓扑模型

```text
                    region（集群边界，region 间零同步）
   ┌────────────────────────────────────────────────────────────────┐
   │                                                                │
   │   zone A                        zone B                         │
   │   ┌──────────┐                  ┌──────────┐                   │
   │   │ node 1   │◄── 全对全 ──┐    │ node 3   │                   │
   │   │ (Spring) │             │    │ (Spring) │                   │
   │   └──────────┘             │    └──────────┘                   │
   │   ┌──────────┐             │    ┌──────────┐                   │
   │   │ node 2   │◄────────────┘    │ node 4   │                   │
   │   │ (Spring) │                  │ (Spring) │                   │
   │   └──────────┘                  └──────────┘                   │
   │        每个节点都持有 region 内【全量】数据，互为副本              │
   └────────────────────────────────────────────────────────────────┘
                  │                                    ▲
                  └──► 共享 MySQL / SQLite（仅管理面）───┘
```

三层空间模型的**部署语义**（语义细节见 [product-overview](../product-overview.md) §3.2）：

| 层 | 部署语义 | 不是 |
|---|---|---|
| **region** | 集群边界 / 复制边界 / 部署边界——一套独立集群，跨 region 零同步 | 不是分片键，不是容量扩展手段（约束 C1、C7） |
| **zone** | 写入准入单位——默认仅同 zone 可注册 / 可发现（可配置放开） | **不是数据局部性单位**——复制仍 region 全量，zone 在拉取端点不生效 |
| **service group** | 服务内流量分组，属管理面数据，无部署形态 | 不是物理隔离 |

### 2.2 集群成员管理

| 项 | 事实 |
|---|---|
| 成员来源 | **静态配置**：`artemis.service.cluster.nodes`（zoneId → urls multimap） |
| 自动发现协议 | **无** |
| 本机识别 | 「URL 包含本机 ip:port」**子串匹配**（脆弱，无结构化身份） |
| 配置变更生效 | ⚠ 发布形态下需**重启**，非热更（基线勘误 §8-13） |
| 存活探测 | 单线程定时任务每 **5s** 逐个调 peer `/api/status/node.json`（3 次重试），结果写 volatile 状态表 |
| 探测形态 | **串行**——节点数多时 5s 周期可能跑不完（基线 §3.1 上限约束） |
| 无 leader / 无自举 | 无选举、无 quorum、无成员变更协议；节点加入 = 改配置 + 重启 |

### 2.3 启动就绪门控（readiness）

节点启动时有**两个目标**（REGISTRY / DISCOVERY）必须同时达成，才置 `canServiceRegistry` / `canServiceDiscovery` 并放行对应 API——**数据不全的节点不接流量**。目标定义、未就绪拒绝口径与已知缺陷（空集群死锁、force-up 旁路、UP 无回退）见 [runtime](runtime.md) §3、[replication-cluster-logic](../domains/replication-cluster-logic.md) §7.3–7.6。

### 2.4 单机演示形态

样例配置开箱可跑的形态是**单节点 + `force-up=true`**：跳过全部初始同步与门控。此时自我保护、复制、门控、故障转移**全部旁路**——演示可用，不代表生产行为。

## 3. 客户端接入拓扑

```text
   宿主进程
   ┌───────────────────────────────────────┐
   │  引导地址（配置，必填，唯一入口）        │
   │        │                              │
   │        ▼  每 5min 拉 up-*-nodes.json   │
   │  存活节点列表（刷新覆盖，失败保留旧）     │
   │        │                              │
   │        ▼  均匀随机取一                  │
   │  当前地址上下文（1h TTL 强制轮换）       │
   │        │                              │
   │        ├─ HTTP /api/*    （失败 → 熔当前地址 → 换址重试 5×100ms）│
   │        └─ WS  /websocket/*（健康检查 1s，会话 5min 强制重建）     │
   └───────────────────────────────────────┘
                │
                ▼
        region 内任一存活节点
```

三级地址容灾的完整状态机与决策规则见 [client-sdk-logic](../domains/client-sdk-logic.md) L3 / D1 / D2 / D3。

| 项 | 事实 |
|---|---|
| 服务端是否感知客户端位置 | 是——客户端上报自身 region/zone；服务端默认只接受同 zone 请求 |
| 就近访问在哪执行 | **宿主 RPC**：服务端不注入就近标记，消费方按 `Instance.zoneId` + 自身位置执行 `close-by-visit` |
| 是否依赖 LB / DNS | 代码不依赖；**生产是否在引导地址前置 LB 不可从代码证实**（部署历史事实，已结项不再追溯，见本文 §6） |
| 客户端是否内置负载均衡器 | **否**——产品只产路由视图 |

## 4. 配置体系架构

### 4.1 配置来源

**配置源由宿主注入**（各组织配置中心不同，不在产品内）。产品自带默认三件套（classpath）：

| 文件 | 职责 |
|---|---|
| `application.properties` | 部署身份：region.id / zone.id / app.id / app.port / app.protocol / app.path |
| `artemis.properties` | 集群成员、租约、复制、限流、门控旁路 |
| `data-source.properties` | 管理面 DB；SQLite 单文件变体（`.sqlite.properties`） |

⚠ 自带三件套均为**静态源**：构造时一次性 load、无文件监听、不发变更事件（[config-reference](../domains/config-reference.md) §0）。

### 4.2 动态更新的三层模型（源 / 声明 / 使用）

一个属性初始化后能否被动态更新，**三层须同时允许**；三层的定义、判断依据与原产品实况见 [product-overview](../product-overview.md) §3.6、[config-reference](../domains/config-reference.md) §0。

**部署视角的落点只有一个——源层由宿主注入**：产品自带三件套是静态源，故声明层（全部属性未声明 static）与使用层虽已就绪，默认部署形态下动态更新**不生效**。

⚠ 基线勘误 §8-13（与 [product-overview](../product-overview.md) §5 勘误 #18 同源）：既有文档「配置全热更」的表述缺**源层前提**，属**部署形态差别，非产品能力缺失**。设计启示（新产品）：把「是否支持动态更新」在**属性定义处显式声明**（如 `isStatic`），好过隐含在代码读取方式中。

### 4.3 配置的部署意义

- 集群成员、region/zone 身份、门控旁路开关**全部来自配置文件**——部署即配置，配置错则节点身份错。
- 无配置中心依赖 → 无外部服务依赖，但也**无集中下发与版本管理**（127 个键模式散落三份 properties，含 5 个死键与 100+ 个代码读取但未发布的键，见 config-reference §7）。

## 5. 部署单元与故障单元

这一节是部署视图的落点：把「部署单元」与「故障单元」「复制单元」对齐，用于重设计时判断哪一层需要重划。

| 单元 | 粒度 | 含义 |
|---|---|---|
| **部署单元** | 一个 Spring Boot 进程 | 接入 + 内核 + 管理面 + 内嵌 Tomcat，不可再拆 |
| **故障单元** | 同上 | 进程崩溃 = 数据面、管理面、接入层**同时**不可用（管理面不能独立存活） |
| **复制单元** | 同上的 peer 集合 | 每节点是 region 内全量副本；写放大 = 每个写操作复制 N−1 次 |
| **容量单元** | region | 无分片——写容量不随节点数扩展，反而随节点数下降（约束 C7） |
| **准入单元** | zone | 写准入 + 可发现性；不是数据边界 |
| **数据持久化单元** | 管理 DB（单实例） | 数据面零持久化，无此单元；DB 成为**唯一持久化点**，却只存治理元数据而非注册数据 |

三处结构性错配，是重设计的直接输入：

1. **故障单元 ⊃ 部署单元 ⊃ 模块边界**——模块隔离未兑现为部署隔离，管理面拖累数据面可用性。
2. **容量单元 ≪ 部署单元集合**——加节点不增写容量，与「对等集群」的直觉相反。
3. **持久化单元与事实源分离**——唯一持久化的是治理元数据，而已注册数据的事实源在**客户端**（约束 C3），全集群重启无 DB 可救（基线 §3.2）。
