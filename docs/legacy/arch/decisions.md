### 结构性优势（跨决策的组合红利）

单条决策的代价见各 ADR 的「代价」节；下面五条是**决策之间配合**才产生的结构性优势，也是总表「继承」倾向的实质内容。逐资产的判断层依据见[基线](../legacy-product-analysis.md) §5。

1. **AP 语义贯彻到底且自洽**——无 quorum / 无 leader / 覆盖写，配五重收敛（复制重试、TTL 丢弃、心跳自愈、peer 全量拉取、客户端 15min 兜底）；每个「不可靠」组件都有上游对账兜底（D1 + D2 + D3）。
2. **读写路径分离彻底**——读路径纯内存 + 后台缓存 + 推送，请求线程上没有锁等待、没有 DB、没有 peer 调用（D4 + D7）。
3. **双轨分离让数据面保持零依赖**——注册 / 发现内核不碰 DB，管理面挂了注册发现照常；模块依赖为**偏序而非链**（D4）。
4. **批量贯穿 + 异步扇出**——API 批量、心跳按进程聚合为一条消息、复制走批量通道；10 万实例量级的立身之本（D2 + D1）。
5. **三层配合让节点故障对客户端近乎无感**——readiness 门控（不接脏流量）+ 三级地址容灾 + 缓存永不失效（D5 + D6 + D8）。

## D1 对等全对全复制，无 leader、无 quorum

**决策**：region 内每个节点互为全量副本，每次写操作扇出到其余 N−1 个节点；无选举、无多数派、无版本向量、无 Raft。

**背景约束**：C1（region 是集群边界）、C7（单 region 单写域）。

**备选方案**

| 备选 | 对比 |
|---|---|
| Leader-based（单主 + 从复制） | 写容量随从节点扩展，但引入选主、脑裂、写路由与故障切换 |
| Quorum / Raft | 强一致、有序，但需多数派可用——与「任一节点可读写」相斥 |
| 分片（按 serviceId 散列） | 写容量与节点数正相关，但需要路由层与再平衡 |
| **全对全（选中）** | 无协调成本、任一节点可读写、实现最简 |

**选择理由**（可证部分）：代码中**零选举、零 quorum、零版本向量**（[replication-cluster-logic](../domains/replication-cluster-logic.md) L1–L4）；冲突处理为「覆盖写 + `creationTime` 新旧保护」，即 AP 语义的直接体现。⚠ 内网规模与运维简单性的动机为**推断**，原仓库无设计文档。

**代价**

| 代价 | 定量 |
|---|---|
| 写放大 | 单节点负载 ∝ `(N−1)`，集群总 ∝ `N(N−1)`（[quality](quality.md) §5.2） |
| 加节点使单节点更忙 | 与「对等集群」的直觉相反——加节点**降**写容量 |
| 无脑裂检测 | 分区时两侧各自接受写，恢复靠覆盖 + TTL 收敛 |
| 无「落后多少」度量 | 无从判断某节点数据陈旧程度 |

**敏感点**：`N` 是唯一可调杠杆，且方向是负的。任何依赖「加节点提容量」的容量规划在本架构上不成立。

## D2 心跳即注册

**决策**：注册不走显式写路径——客户端本地实例集是**唯一事实源**，每 5s 把全量实例作为心跳上报，服务端以此完成注册 + 续约。显式 register API 只用于补报。

**背景约束**：C3（数据面零持久化）、C4（客户端缓存永不失效）。

**备选方案**

| 备选 | 对比 |
|---|---|
| 显式注册 + 独立续约（如 Eureka 的 register + renew 两接口） | 语义清晰，但需要两套状态机与两次往返 |
| 第三方健康探测（服务端主动探测实例） | 服务端掌握真实状态，但需探测协议与网络可达性 |
| **心跳即注册（选中）** | 一条通道完成注册、续约、对账；天然幂等 |

**选择理由**：天然幂等对账——服务端重启 / 客户端重连后，下一轮心跳自动完成重注册，无需补偿逻辑；断网续注册免费获得。上报即全量，使服务端无需理解增量语义。

**代价**

| 代价 | 说明 |
|---|---|
| 服务端无法验证真实性 | 客户端自报，无第三方核验（C6） |
| 全量上报的带宽 | payload = 进程全量实例集，随进程实例数线性增长 |
| 语义与 TTL 耦合 | 「心跳驱动消息率」与「TTL 驱动摘除」是两条独立时间轴，易被混为一谈（[quality](quality.md) §5.2 口径勘误） |
| 首次可见有延迟 | ≈ 6s（1 心跳间隔 + 补注册往返） |

**敏感点**：`心跳间隔 (5s)` 与 `实例 TTL (20s)` 的比值决定误摘除的容忍度；原产品用**自我保护**（D8）而非调整比值来兜底。

## D3 注册表零持久化

**决策**：注册数据纯内存（`ConcurrentHashMap`），无任何写盘；进程重启即空，靠 peer 全量拉取 + 客户端重注册重建。

**背景约束**：C3。

**备选方案**

| 备选 | 对比 |
|---|---|
| 全量持久化到 DB | 可恢复，但把写路径变成 DB 依赖（破坏 C8、C9 的零依赖红利） |
| 周期快照 / WAL | 折中，但引入了快照一致性、恢复时间与磁盘容量问题 |
| 客户端本地快照（如 Eureka 的本地 registry 副本） | 客户端侧兜底，改动面小 |
| **零持久化（选中）** | 写路径最快，读路径纯内存，零外部依赖 |

**选择理由**：与 C8（数据面组件不依赖 DB）互为因果——数据面不碰 DB 是双轨分离（D4）的基石。事实源在客户端（D2），服务端本就不必是权威。

**代价**

| 场景 | 后果 |
|---|---|
| 全集群同时重启 | **无 DB 可救**，依赖客户端风暴式重注册 |
| 服务端全挂 + 客户端也重启 | **发现完全不可用**（客户端亦无磁盘快照，C4） |
| 冷启动 | 必须至少一个存活 peer，空集群死锁（[runtime](runtime.md) §3.3） |

> 对比：Eureka / Nacos 均有磁盘 snapshot。原产品**两侧同时无持久化**，是该决策最大的结构性缺口。

## D4 数据面 / 管理面双轨分离

**决策**：注册表（数据面）纯内存零 DB；流量治理元数据（管理面）走 MySQL/SQLite。管理面经**注入点**作用于数据面，两者不共享存储、不共享事务。

**背景约束**：C8（数据面不依赖 DB）、C9（内核零 Spring、模块单向）。

**备选方案**

| 备选 | 对比 |
|---|---|
| 统一存储（注册数据与治理元数据同库） | 简单，但把数据面绑上 DB——DB 故障即注册中心故障 |
| 治理能力内建进数据面 | 无跨面延迟，但数据面复杂度与依赖陡增 |
| **双轨 + 注入点（选中）** | 数据面保持零依赖；管理面可整体关闭 |

**选择理由**：可证的结构性红利——`artemis.management.enabled=false` 时零外部依赖；模块依赖链单向；内核零 Spring。管理面故障（DB 挂）不影响注册发现。

**代价**

| 代价 | 说明 |
|---|---|
| 跨面一致性靠时序 | 写后 `waitForPeerSync()` = `Thread.sleep(2s)`；**写成功 ≠ 全网生效** |
| 无生效确认 | 无回执、无版本、无「已生效节点数」查询 |
| 隔离未兑现为部署隔离 | 同进程（[deployment](deployment.md) §5）——管理面挂了数据面仍受 JVM 资源池拖累 |
| 注入点数量 | 5 个接入点（3 个作用于数据面），是隐式耦合面 |

**敏感点**：`sleep(2s)` 是**一致性赌注**而非机制。重设计若保留双轨，必须把「生效确认」做成可查询的状态（版本 / 世代 / ack 数），而不是 sleep。

## D5 静态集群成员

**决策**：集群拓扑来自配置（`artemis.service.cluster.nodes`，zoneId → urls multimap）；无自动发现、无成员变更协议；本机识别用「URL 包含本机 ip:port」子串匹配。

**背景约束**：C5。

**备选方案**

| 备选 | 对比 |
|---|---|
| 共识成员管理（Raft / gossip） | 动态加入退出，但引入共识复杂度与自举问题 |
| 外部协调服务（ZooKeeper / Etcd / K8s API） | 复用成熟组件，但引入外部依赖（违反 C8 的零依赖倾向） |
| **静态配置（选中）** | 零依赖、零协调、行为完全可预测 |

**选择理由**：与「无 leader、无 quorum」（D1）自洽——既然不需要协调，就不需要成员协议。⚠ 动机为**推断**。

**代价**

| 代价 | 说明 |
|---|---|
| 扩缩容需改配置 + 重启 | 发布形态下配置变更是**静态源**，不热更 |
| 串行探测 | 5s 周期逐个 HTTP 探测，节点多时跑不完 |
| 子串识别脆弱 | ip:port 子串匹配，多网卡 / NAT / 端口复用场景易误判 |
| 无自举 | 空集群死锁；节点加入靠运维 |

**敏感点**：「节点数」在本架构中同时是容量负因子（D1）、探测负载因子（串行）与配置维护成本因子——三重叠加。

## D6 Smart client + 缓存永不失效

**决策**：客户端嵌入宿主进程，自带三级地址容灾、熔断换址、内存缓存；**缓存永不失效**——服务端全挂时继续返回最后一份快照，以陈旧换可用。

**背景约束**：C4。

**备选方案**

| 备选 | 对比 |
|---|---|
| Thin client + 服务端代理 / Sidecar | 客户端轻，但每跳增加延迟与故障点 |
| DNS / LB 前置 + 纯查询客户端 | 无需 SDK，但丢失订阅推送与本地容灾 |
| **Smart client（选中）** | 零额外跳数、服务端不可用时仍可发现 |

**选择理由**：可证——三级容灾管线（引导地址 → 存活列表 → 随机选址 + 熔断 + TTL 轮换）完整实现；服务端全挂时 `getService` 继续返回快照。

**代价**

| 代价 | 说明 |
|---|---|
| 每 manager 7+ 线程 | 客户端线程随进程数线性放大 |
| 缓存无上限、无淘汰、无配额 | 订阅面大的客户端内存只增不减 |
| 宿主强耦合 | 无 Spring Boot starter、无多语言 SDK；绑定 org.mydotey.* 自研库栈（已发布 Maven Central，见[基线](../legacy-product-analysis.md) §8-14 勘误，非不可得，但生态面窄） |
| 无 close API、回调线程 non-daemon | **阻止宿主 JVM 退出** |
| 无状态查询 | 宿主无法感知 SDK 是否可用 |
| 熔断不排除地址 | 坏节点无冷却、无失败计数，仅作废当前上下文 |

**敏感点**：「永不失效」是可用性换正确性的显式取舍，但**缺两样配套**：本地磁盘快照（否则客户端重启即失效）与缓存容量上限（否则 OOM）。重设计可保留语义、补齐配套。

## D7 推送为主 + 三层兜底轮询

**决策**：变更以 WS 订阅推送（at-most-once）为主；60s 三层兜底轮询（reload 失败的服务 / 实例为空的服务 / 超 15min TTL 的全量）兜住漏推。

**背景约束**：—

**备选方案**

| 备选 | 对比 |
|---|---|
| 纯轮询 | 实现最简，但延迟下限 = 轮询周期，服务端读压力 ∝ 客户端数 |
| 纯推送 | 延迟最低，但漏推 = 永久不一致 |
| **推送 + 兜底（选中）** | 常态低延迟 + 有界不一致 |

**选择理由**：推送使常态变更亚秒级可见；兜底使最坏情况有上界。二者叠加是可用性设计的正确形态。

**代价**

| 代价 | 说明 |
|---|---|
| 不一致窗口无度量 | 无数据版本 / 世代，「落后多少」不可知；最坏只能等 15min |
| 推送管线脆弱 | 10 worker **同步发送**，无 per-subscriber 队列——慢消费者占满 worker 即全管线停滞 |
| 客户端回调无界队列 | 单线程 + 无界，慢消费者 OOM |
| delta 接口未消费 | 服务端实现完整，客户端增量完全靠 WS（死能力） |
| `CHANGE` 类型零产生点 | 客户端 CHANGE 分支等价 NEW（[product-overview](../product-overview.md) §5 勘误 #3） |

**敏感点**：`15min` 兜底 TTL 是全架构**唯一的不一致上界**——它同时是可用性保证与容量账（每次全量批量 lookup）。

## D8 租约 TTL + 自我保护（被动探测）

**决策**：实例存活 = 租约未过期；清理线程每秒全表扫描摘除过期租约；Eureka 式**自我保护**——窗口续约量低于历史峰值 85%（峰值 ≥ 50 才启用）时，跳过所有「仅过期未显式 evict」的清理。

**背景约束**：C6（服务端不做健康探测）。

**备选方案**

| 备选 | 对比 |
|---|---|
| 服务端主动健康探测 | 状态更真实，但需探测协议、超时策略与网络可达性保障 |
| 缩短 TTL / 调大心跳比 | 简单，但会放大误摘除与网络抖动敏感度 |
| 停用自我保护 | 大面积网络故障时批量摘除——引发级联故障 |
| **被动探测 + 自我保护（选中）** | 零额外流量，用统计阈值区分「网络故障」与「真的挂了」 |

**选择理由**：可证——`LeaseUpdateSafeChecker` 以滑动窗口续约量对比历史峰值判定；统计量暴露于 `leases.json`。

**代价**

| 代价 | 说明 |
|---|---|
| 保护态静默 | 保护期间过期实例**不被摘除**，消费方可能拿到已死实例 |
| 阈值不可解释 | 85% / 峰值 50 是经验值，无自适应 |
| 不覆盖显式下线 | 自我保护与「显式 unregister 不受保护」的语义边界需重申（[product-overview](../product-overview.md) §6） |
| 摘除延迟 | 21s（TTL 20s + clean 1s） |
| 全表扫描 | 每秒扫描全表，百万级需分片 / 时间轮 |

**敏感点**：自我保护与 TTL 是**重叠的两个兜底**——两者共同决定「服务端认为实例是否活着」，但只有前者可被观测（`leases.json`），后者不可。重设计需明确二者职责边界。

## D9 WS + JSON 作接入协议

**决策**：注册心跳与变更推送走 WebSocket，报文为 JSON 文本；Readme 宣称的 gRPC 未兑现。

**背景约束**：—

**备选方案**

| 备选 | 对比 |
|---|---|
| gRPC / HTTP2 | 多路复用、二进制、强 schema、跨语言——但需 proto 治理与代码生成 |
| 二进制 WS（如 protobuf / MessagePack） | 带宽与解析优于 JSON，兼容性成本低 |
| 纯 HTTP 长轮询 | 无长连接状态，但延迟与连接开销高 |
| **WS + JSON（选中）** | 浏览器 / 通用库支持最好，调试最方便 |

**选择理由**：⚠ **无源码证据**——原仓库无设计文档；Readme 曾宣称 gRPC（基线 §4 判定「未兑现」）。可推断的合理性在「2016 年代的通用选型 + 调试友好」。

**代价**

| 代价 | 说明 |
|---|---|
| 文本缓冲上限 | 客户端默认 **8KB**，与大规模服务报文体量不匹配；超限断连重连 |
| 序列化开销 | JSON 文本解析，无 schema |
| 两套 WS 通道职责不同 | 心跳上报 / 变更推送各一套端点与 `WebSocketSessionContext`，线程与限流逻辑重复 |
| 三通道不统一 | REST / WS / 复制为三套独立传输实现，序列化与重试策略各写一遍 |
| 无协议版本协商 | 协议变更无法灰度 |

**敏感点**：`8KB` 上限与「批量、全量、10 万实例」的叙事直接冲突——这是协议选型与容量目标不匹配的**最具体的一处证据**。

## D10 只产路由视图，不执行路由

**决策**：产品只生产 `instances` / `logicInstances` / `routeRules` 视图，**不做负载均衡**；选址由宿主 RPC 框架按 `RouteRule.strategy`（weighted-round-robin / close-by-visit）执行。

**背景约束**：—

**备选方案**

| 备选 | 对比 |
|---|---|
| 内建 LB（客户端或服务端） | 开箱即用，但与宿主已有 RPC 层职责重叠、双份治理 |
| Sidecar / 代理 | 语言无关，但引入部署形态变化与网络跳数 |
| **只产视图（选中）** | 产品边界清晰，选址策略交给 RPC 层 |

**选择理由**：可证——服务端不注入就近标记，消费方按 `Instance.zoneId` + 自身位置执行就近逻辑；服务端 `up-nodes` 无排序（[product-overview](../product-overview.md) §5 勘误 #2）。

**代价**

| 代价 | 说明 |
|---|---|
| 就近能力依赖宿主配合 | 服务端只给 `zoneId`，不保证宿主真的执行 close-by-visit |
| zone 参数在拉取端点不生效 | 不是数据局部性单位（C2），语义易被误解 |
| 无端到端延迟可见性 | 产品看不到实际选址结果与调用延迟 |

**敏感点**：这是产品**边界**决策而非技术决策——它决定了「就近访问」「负载均衡」永远只能是**协作能力**，不能是本产品的能力。

## D11 无内置安全，信任内网部署

**决策**：全 API 无认证鉴权、明文 http/ws、无 TLS；唯一屏障是 WS IP 黑名单与 region / zone 软隔离。

**背景约束**：C10。

**备选方案**

| 备选 | 对比 |
|---|---|
| 内建认证 + TLS | 可公网部署，但需密钥管理、证书轮换与性能开销 |
| 依赖服务网格 / mTLS（外部设施） | 复用基础设施，但绑定部署形态 |
| **信任内网（选中）** | 零开销、零密钥管理、内网假设下边际收益低 |

**选择理由**：⚠ **推断**——原为携程内网产品，`no-permission` 错误码有定义**但无实现**，说明设计时预留过权限语义而后未落地。

**代价**

| 代价 | 说明 |
|---|---|
| **开源形态不可上生产** | 摘除实例、改路由权重**无任何身份校验** |
| DB 密码明文 | 样例 `admin/123456` |
| Token 只存不验 | 管理面 `OperationContext.token` 是装饰 |
| region / zone 不是安全边界 | 同 region 内任何客户端可操作任意服务 |

**敏感点**：这一条**不能继承**。安全是重设计的必做项而非可选项；同时它会反向影响 D9（协议需支持 TLS 与凭据）与 D4（管理面鉴权是独立信任域）。
