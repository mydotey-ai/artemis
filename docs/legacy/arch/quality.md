## 1. 错误处理

`ErrorCodes` 是全产品唯一的错误语义来源，贯穿三条链路：客户端处置决策（rerunnable / serviceDown 划分）、复制重投决策、HTTP 状态映射。**码表与逐码处置见 [product-overview](../product-overview.md) §3.1**，本文只记结构性缺口。

### 1.1 两处不闭合

- `no-permission` **只由 region / zone 准入产出**（`RegistryTool`、`DiscoveryServiceImpl`、`RegistryReplicationServiceImpl`），**没有任何认证鉴权产出它**——即「权限」语义存在，但身份校验不存在（见 §2）。⚠ [基线](../legacy-product-analysis.md) §3.6 记作「定义了但无实现」，指的是无**鉴权**实现，不是无产出点。
- **无全局异常处理**——畸形 JSON 请求返回框架默认 400，**不是** `ResponseStatus` 结构（[product-overview](../product-overview.md) §6）。

### 1.2 错误传播形态

| 层 | 形态 |
|---|---|
| 服务端 REST | 统一 `ResponseStatus` 结构 + `failedInstances` 部分失败语义 |
| 服务端 WS | 心跳响应携带 `failedInstances`，逐实例 errorCode |
| 客户端 | 错误码驱动决策，不暴露原始 HTTP 码 |
| 复制 | 错误码 → `TaskErrorCode`（PermanentFail / RerunnableFail / RateLimited）→ 重投或丢弃 |
| 发现过滤器链 | **逐 filter try/catch fail-open**——单个 filter 异常不阻断发现 |

**吞错点**：WS 心跳解析异常回**固定 success**（错误被吞掉）；客户端首次 `getService` 失败静默返回空 Service（[client-sdk-logic](../domains/client-sdk-logic.md) §7.3）；fail-open 是刻意设计，但意味着过滤器故障对消费方**不可见**。

## 2. 安全

**现状：几乎为零**，且不是配置疏漏而是开源形态的内网假设——全 API 无认证鉴权、明文 http/ws 无 TLS 配置点、DB 密码明文（样例 admin/123456）、管理面 `OperationContext.token` 只存不验、管理写接口（摘除实例 / 改路由权重）同样无身份校验。唯一屏障是 WS IP 黑名单。

**结构性缺口**：region / zone 是**业务准入单位，不是安全边界**——同 region 内任何客户端可注册或摘除任意服务。**开源形态不可上生产**（基线 §3.6），安全边界是重设计的必做项而非可选项（见 [decisions](decisions.md) D11）。

## 3. 可观测性

**结构性缺口**：metric / trace 埋点点位完整，但开源实现是**空壳**（`MetricLoggerHelper` 方法体为空、默认 `NullProvider`）；无指标时间序列、无告警、无 traceId 贯穿。**事实上的排障面是状态 API 的轮询式人工查阅**——`config.json`（全配置 + 来源）与 `leases.json`（租约明细 + 自我保护统计）是主力，另有 `cluster.json` / `deployment.json` / ws 连接数。

后果：10 万实例规模下「当前是否处于保护态」「哪个节点落后多少」**无法自动回答**，`leases.json` 只给瞬时快照。审计侧机制与缺陷见 [product-overview](../product-overview.md) §5 勘误 #10。

## 4. 限流

统一由 Caravan `RateLimiterManager` 提供，**全通道超限返回 `rate-limited` 而非挂死**（10s 窗口）：registry 100k / replication 1M / cluster（up-nodes）10k / status 30 / management.group 30（阈值明细与死键见 [config-reference](../domains/config-reference.md) §2.6）。

**结构性缺口**：**发现查询通道（lookup / getService / getServices）无限流配置**——读路径未受保护，而它恰是消费方高频调用的路径。另注：`status` 限流 30/10s 意味着排障通道本身也被限流。

## 5. 定量容量模型

本节是原调研的**主要空洞**。以下把散落的容量相关常量集中，并给出可推导的公式。

> **性质声明**：§5.1 的参数是**源码 / 配置事实**；§5.2–§5.5 是**在明确假设下的推导**，非源码事实，也未做过实测（原仓库无压测报告）。推导用于暴露结构性上限，不得当作实测容量。

### 5.1 容量相关参数（源码事实）

| 参数 | 值 | 出处 |
|---|---|---|
| 心跳间隔 | 5s | 客户端 `.instance-registry.heartbeat-interval` |
| 实例 TTL | 普通 20s / legacy 90s | `artemis.properties` |
| 注册表初始容量 / 上限 | 默认 1 万 / 10 万 | 配置范围 |
| 变更跳表阈值 | 10,000 条 | 超则丢最早 |
| 复制 workQueue 逻辑阈值 | 10,000 | 超则丢最旧（⚠ 批量通道保护失效，见 [runtime](runtime.md) §2.2） |
| 复制批量 | 250 条 / 攒批延迟 2s | 心跳通道 |
| 复制任务 TTL | 5s | 自首次提交起算 |
| 复制线程 | 2 × 20 = 40 | ⚠ 配置键拼写错误，实际取默认 |
| 服务端后台线程总数 | ≈ 67 | [runtime](runtime.md) §1.2 |
| 客户端每 manager 线程 | 7+ | [runtime](runtime.md) §1.3 |
| 版本化快照 | 30s 周期 × 保留 3 份 | 全量 |
| WS 文本缓冲（客户端） | 8KB（上限 32KB） | 超限断连 |

### 5.2 心跳与复制负载模型（推导）

**关键前提**：心跳是**按 manager（进程）**发的一条消息，payload 是**该进程的全量实例集**——不是每实例一条消息。

设：`I` = 实例数，`P` = 持有实例的进程数，`N` = region 内节点数，**客户端进程均匀落在 N 个节点上**（每个节点承接 `P/N` 个进程的写）。

| 量 | 公式 | 10 万实例、P = 5,000、N = 5 时 |
|---|---|---|
| 心跳消息率（全集群） | `P / 5` msg/s | 1,000 msg/s |
| 实例条目率 | `I / 5` entries/s | 20,000 entries/s |
| 单节点**发起**的复制 | `(P/5) × (N−1)/N` msg/s | 800 msg/s |
| 单节点**接收**的复制 | `(P/5) × (N−1)/N` msg/s | 800 msg/s |
| 集群复制**总投递量** | `(P/5) × (N−1)` msg/s | 4,000 msg/s |

**写放大结论**（两者方向不同，别混）：

- **集群总投递量 ∝ `N−1`**——线性增长，加一个节点就多一份全量扇出。
- **单节点投递量 = `(P/5)(1 − 1/N)`**——随 `N` 上升但**有界**，趋近 `P/5` 而永不超出。

合起来才是约束 C7 的准确表述：**加节点不提升单节点可承载的写容量**（单节点负载趋近其上界），只让集群总负载线性膨胀。原产物把「对等集群」宣传成可水平扩写，与这条定量事实相反。

> ⚠ **与基线的口径差异**：[基线](../legacy-product-analysis.md) §3.1 的 `×(N−1)` 方向是对的，但基数「10 万实例 × TTL 20s ≈ 5k 心跳/s」把 **TTL 当成了心跳周期**（默认是 5s），且按**实例数**而非**进程数**计——心跳是按 manager 聚合的一条消息，自变量是进程数。

代入上式（P = 5,000）：`N=3` → 单节点 667 msg/s、集群 2,000；`N=5` → 800 / 4,000；`N=20` → 950 / 19,000——**单节点渐近饱和于 1,000，集群总量继续线性涨**。

### 5.3 内存与栈预算（推导）

| 项 | 模型 | 10 万实例时 |
|---|---|---|
| 注册表单副本 | `I` × 每实例开销（Instance 13 字段 + Lease + CHM entry + 字符串） | 见下 |
| 每实例开销 | 保守 0.5 KB（字符串占主导：url / ip / machineName / metadata） | 50 MB |
| 每实例开销 | 宽估 1 KB（含 metadata map 与对象头） | 100 MB |
| 变更跳表 | 10,000 × 每变更条（含 Instance 引用） | ≈ 10 MB |
| 版本化快照 ×3 | 3 × 服务壳 + Instance 引用（**引用共享，非深拷贝**） | 与快照服务数相关 |
| 后台线程栈 | 67 × 1 MB（默认 `-Xss`） | 67 MB **虚拟**（提交远小于此） |

**结论（数量级）**：10 万实例的原始注册数据在 **百 MB 量级**——内存不是主要天花板；真正的天花板是**写放大**（§5.2）与**客户端缓存无上限**（§5.4）。

### 5.4 客户端资源模型

| 项 | 性质 |
|---|---|
| 缓存服务数 | **无上限**——`ServiceRepository` 缓存永不失效、无淘汰、无配额 |
| 每服务每实例开销 | `getService` 每次都 clone 外壳 + **全量重建路由 Map**；Instance 元素引用共享（[client-sdk-logic](../domains/client-sdk-logic.md) §7.6） |
| 消费方内存 | ∝ 订阅服务数 × 每服务实例数 × 克隆开销；服务端全挂时**只增不减** |
| 回调队列 | 单线程**无界**队列，负载 = 整服务克隆快照；慢消费者 → 堆积 → OOM |
| 线程 | 每 manager 7+ |

**结构性问题**：消费方内存占用**没有任何配额或背压**，且服务端不可用时缓存只增不减——高订阅面客户端在这种形态下没有内存上限保障。

### 5.5 延迟预算

| 场景 | 时延量级 | 构成 |
|---|---|---|
| 首次注册可发现 | ≈ 6s | 1 心跳间隔（5s）+ 补注册往返 |
| 实例宕机摘除 | ≈ 21s | TTL 20s + clean 周期 1s |
| 运维摘除生效 | ≈ 1–3s | API 含 `sleep(2s)` + 1s 刷新 + 推送 |
| 灰度权重生效 | ≈ 5–7s | 5s 刷新 + reload + 消费方重拉 |
| 节点故障（客户端视角） | 毫秒–秒级 | 错误码熔断 + 换址重试（5 × 100ms） |
| 推送漏推的纠正上限 | **15min** | 三层兜底的全量刷新 TTL |
| 节点冷启动 | 数据量相关 | peer 全量拉取 |

> **没有「落后多少」的度量**：无数据版本 / 世代概念，消费方无法量化自己的视图比服务端落后多少；最坏情况只能等 15min 兜底。

### 5.6 上限约束

**`N`（region 节点数）是唯一的硬约束**——它同时抬高集群总投递量（∝ `N−1`）和单节点投递量（→ `P/5` 的上界），而**不抬高任何节点的可承载写入量**（§5.2）。其余均为软上限（clean 全表扫描、串行探测、10 worker 同步推送、8KB 文本缓冲），可通过实现改进提高。**唯一「无界」项是消费方订阅面**：客户端缓存无配额、无淘汰、无背压（§5.4）。

## 6. 演化与兼容

### 6.1 版本策略

| 维度 | 现状 |
|---|---|
| API 版本 | **无版本号、无路径版本段**（统一 `/api/` 前缀，无 `/v1/`） |
| 协议协商 | **无**——无能力协商、无 schema 版本 |
| 数据格式版本 | **无**（DB 无版本表、无迁移脚本） |
| 灰度发布能力 | 仅**业务级**（路由权重两段式灰度）；**技术级**（协议 / 版本）无 |

### 6.2 兼容包袱（现存）

| 包袱 | 说明 |
|---|---|
| 双租约池（20s / 90s） | 为兼容老客户端（`metadata.java_registry` 非空）保留的过渡设计 |
| `legacy-leases` 状态端点 | 配套双池的存在 |
| HTTP 心跳端点 | 已判为**死端点**，为旧代客户端保留的推断未证实（[product-overview](../product-overview.md) §7） |
| `destroyServers` 批量物理删除 | **死代码**（无端点无调用方） |
| 私有依赖链 `org.mydotey.*` | scf / rpc-util / caravan / codec / lang-extension **均不在 Maven Central**——外部落地必须**连号移植整条链** |
| 技术栈定格 2020-12 | Java 8、Spring Boot 2.3.6（EOL）、javax 命名空间、springfox 3.0.0（已死项目）、HttpClient 4.x、Jackson 2.12、MySQL Connector 5.1.49、JUnit 4.13 + Mockito 1.10 |
| 模块改名遗留 | 部署章节仍指向 `artemis-web/...`，路径全部过期（基线 §4） |

### 6.3 迁移路径

**无**。没有数据格式版本化、没有升级脚本、没有滚动升级协议约束（节点间无版本握手，滚动重启期间新旧节点直接互连复制）。双租约池是原产品**唯一**体现出的「版本兼容设计」，且仅覆盖 TTL 一个维度。

> 对重设计的意义：**「可安全滚动升级」是一项从零开始的能力**，不是既有能力的改进。
