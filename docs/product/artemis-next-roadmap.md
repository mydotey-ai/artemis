# 新一代 Artemis 产品规划与版本路线图

版本: 1.12    更新时间: 2026-10-23

> 本文是新一代 Artemis 的产品规划与版本路线图：定位与成功标准、迭代式版本切分（每版可发布可 eval）、各版本范围与验收要点。架构设计详见 [架构设计](../arch/artemis-next-architecture.md)；设计输入见 [原产品能力基线](../legacy/legacy-product-analysis.md) 与[行业对标报告](../legacy/industry-benchmark.md)。

## 1. 定位与成功标准

**定位**：开源服务注册中心，对标 Nacos；具备原产品（支撑过 10 万+ 实例）的核心能力并现代化。

**成功标准**：

1. 外部用户可 eval（Docker 单机容器一条命令起全功能）；
2. 可上生产（默认认证、可观测、可运维、容量基线公开）；
3. 单集群 10 万实例级（批量与聚合心跳从第一天就是设计输入）；
4. 治理能力（灰度/摘除/逻辑实例）构成对标 Nacos 的差异化。

**迭代策略**：垂直切片——每个版本都是可发布、可 eval 的完整小产品；逐服务开发（registry → discovery → management）；模块边界与 proto 契约 v0.1 就按三服务定，后拆代价大；集群语义 v0.1 进架构、v0.2 交付。

## 2. 版本路线图总览

| 版本 | 主题 | 治理期 | 可发布物 |
|---|---|---|---|
| v0.1 | registry 单服务 | 期 1 前半 | 单节点 registry + management（内存态管理面）+ Java 8 SDK（注册侧） |
| v0.2 | registry 集群 | 期 1 后半 | 多节点集群可部署 |
| v0.3 | discovery | 期 2 | 完整发现闭环 + 消费方 SDK + 多集群聚合 |
| v0.4 | 治理面 I | 期 3 | management + DB + console 只读 |
| v0.5 | 治理面 II | 期 3 | 差异化治理能力完整 |
| v1.0 | GA | — | 生产就绪：安全完整、三种部署形态、容量基线 |
| v1.x | 生态与多语言 | — | Go/Rust SDK、Rust 混合集群、规模选项 |

## 3. 各版本范围

### v0.1 registry 单服务

- **内核**：注册模型显式四操作（register/deregister/update + 心跳全量上报续约/补注册，心跳走 gRPC 双向流，D12）、租约/过期清理、自我保护基础版（窗口阈值 + 指标暴露）、服务端快照落盘 + 重启回放、readiness 门控、成员抽象接口（静态实现，单成员起步）。
- **接入**：gRPC + HTTP 双协议；内部/外部端口分离。
- **治理期 1 前半**：management-service 起步（内存态）——实例管理 Admin API（列表/详情/摘除/恢复）+ 状态 API 排障面（leases/config 类）；registry 提供只读事实查询 RPC，摘除记录归 management（ADR-016）。
- **安全**：默认开启的单账户认证。
- **可观测**：metrics（Micrometer/Prometheus）+ 结构化 log + OpenTelemetry trace，第一天内建。
- **客户端**：Java 8 SDK 注册侧——心跳客户端、实例管理、生命周期 API（close/优雅下线）、三级地址容灾骨架；随附 Spring Boot starter（注册侧自动装配）。注册侧不做客户端磁盘快照：注册事实源是业务代码自身，重启后业务重新注册 + 心跳幂等收敛天然自愈；磁盘快照归发现侧 SDK（v0.3，消费方服务列表缓存 + server 全挂兜底）。
- **工程**：monorepo 目录布局与 Maven 多模块（第一天就定，见技术选型 §2.1；三服务边界同此）、proto 契约（六组 proto：common 公共数据模型 + 五组 service proto，数据模型含 namespace 字段——架构 D10）、CI、Dockerfile。
- **验收要点**：单节点起停、SDK 注册/心跳、实例经状态/管理 API 可观测、摘除/恢复经管理查询 API 的**有效视图**（已应用摘除过滤）可验证、快照重启回放、认证生效、指标可抓取。（服务发现查询归 discovery，v0.3 起验收）

### v0.2 registry 集群

> 管理面说明：v0.1 起管理的摘除记录由 management-service 持有，registry 集群不感知摘除；v0.2 不引入摘除记录集群扇出。management 保持单节点，v0.4 接 DB。

- 静态成员集群（配置驱动）、变更事件扇出（增量小报文 + 批量 + 指数退避重试）、peer bootstrap 全量、丢失自愈链（变更再扇出 + 客户端 TTL 轮换 + bootstrap）。
- 自我保护 2.0：按服务粒度阈值、保护态显式可观测（指标/API）；保护态为 registry 内部概念，不进 discovery 分发契约（2026-10-23 裁决）。
- SDK：三级地址容灾完整（熔断换址）+ 连接 TTL 轮换（默认 10min ± 抖动）。
- 节点状态 API、优雅停机（先标记自身下线再停止，客户端凭容灾换址，无需连接迁移）。
- **验收要点**：3 节点集群、节点故障客户端无感换址、杀节点数据最终一致、保护态可观测。

### v0.3 discovery

- discovery-service：bootstrap 全量 + 变更流投影（`(cluster, namespace, service)` 模型，分组以实例 metadata 表达）、订阅推送（推拉结合：增量流一流多目标 + hash 对账 + 全量拉兜底，ADR-019）、三层兜底轮询、查询 API、新鲜度标记（上游连接状态；registry 保护态不在此列）。
- **多集群聚合**：单节点订阅多个 registry 集群，本地合并（union + 选择器过滤）。
- **治理依赖（0..1）**：订阅 management 的摘除规则并应用过滤；完整治理规则链随 v0.4。
- 治理期 2：发现管理 API（订阅关系查看、服务视图、上游状态/新鲜度）。
- registry + discovery **all-in-one 打包**（同进程双 server 双端口）。
- 客户端：消费方 SDK——订阅、本地缓存、磁盘快照、兜底轮询、地址容灾（配置地址列表 + 历史成功连接缓存 + 熔断换址；discovery 无服务端存活列表，见架构 §2.1）、Spring Boot starter（发现侧自动装配补全）。
- **验收要点**：推送亚秒可见、断连自愈、多集群 union 查询、all-in-one 单包起。

### v0.4 治理面 I（management + DB）

- management-service（v0.1 起已有内存态管理面）：DB 接入（MySQL/PG 双方言 + Flyway migration）、账户体系（单管理员，统一认证）。
- **四级摘除持久化**（instance → server → zone → group）+ 操作记录即状态 + 审计。
- **逻辑实例**（静态实例纳入统一发现视图）。
- 规则下发闭环：规则版本 + 订阅流 + discovery ack + 生效水位（替换盲下发）。
- discovery 过滤器链扩展（治理启用时依赖 management，0..1 配置；v0.3 已接摘除规则）。
- console 只读版：服务列表/详情/搜索（分页 + 模糊）、实例视图。
- 三服务 **all-in-one 完整形态**。
- **验收要点**：摘除跨重启恢复（management 重下发）、规则生效水位可见、逻辑实例可发现、console 可用。

### v0.5 治理面 II（治理能力完整）

- 分组路由（Group filter 全语义，分组以实例 metadata 表达）、**两段式权重发布**（`weight/unreleased_weight` + release）+ **diff 预览 + 一键回滚**、canary（自动专属规则组）。
- console 管理版：发布/摘除操作、订阅关系视图（调用方视角）、操作审计流、自我保护态展示。
- **验收要点**：灰度发布端到端（一个 API 完成）、回滚生效、canary 流量切分。

### v1.0 GA（生产就绪）

- **安全完整**：TLS（内外通道可启）、RBAC（角色 × 资源 × 动作）。
- **容量验证**：10 万实例压测，发布容量基线文档（内存/带宽/QPS/推送延迟）。
- **三种部署形态**：Docker 单机容器（eval）、虚拟机标准安装包（tar.gz + systemd）、K8s/Helm chart（三服务独立编排）。
- 文档站（快速开始/配置参考/API 参考/运维手册）；SDK 与 starter 发布 Maven Central。
- 滚动升级协议验证：proto 前后兼容 + 集群节点滚动重启（客户端容灾无感）。
- **验收要点**：压测报告公开、三种形态各自一条命令/一套流程拉起、集群滚动升级无感、安全审计通过。

### v1.x 生态与多语言（顺序可调，按需排期）

- Go SDK → Rust SDK。
- **Rust registry 节点（混合集群）**：数据面 proto 冻结后实现，与 Java 节点同集群互通。
- 主动健康检查（可选能力，默认关闭，延续「实例状态客户端自报」哲学）。
- 负责制分片（20+ 节点规模选项）。
- 动态成员（K8s 成员源）。

## 4. 后置项与风险

| 项 | 处置 |
|---|---|
| Rust 混合集群排 v1.x 后段 | 数据面协议经 v0.2–v1.0 稳定后才冻结契约，避免重写 |
| 负责制分片 | 全对全 + 增量在 ≤10 节点无压力；20+ 节点或高变更率时启用（协议兼容增量事件，无需换协议） |
| 期 1 内存摘除重启丢失 | 设计内行为（文档明确）；期 3 DB 接管后闭环 |
| 主动健康检查 | 默认哲学是客户端自报；作为可选项后置 |
| 审批流（治理操作） | 基线 #18 子项；v1.x 按社区需求排期 |
| 发现通道限流 | 对标报告第二层项；v1.x 按压测结果决定（先以兜底轮询 + 背压保护） |
| 10 万实例容量 | 机制继承自原产品（批量/聚合心跳），v1.0 压测验证兜底 |
